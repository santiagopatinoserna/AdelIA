# AdelIA — v0.1 Design Spec

## 1. Visión

**AdelIA es una plataforma open source de soberanía de datos médicos personales.**

Cada persona puede volcar TODA su historia clínica (PDFs, fotos de labs, recetas, audios de citas grabadas) en un sistema RAG temporal. El sistema organiza la data automáticamente y permite:

- Consultas en lenguaje natural ("dame la curva de azúcar de los últimos 10 años")
- Briefings adaptativos por especialidad antes de cada cita médica
- Compartir contexto controlado con médicos vía link efímero, QR, PDF o email
- Auto-hosting completo (Docker Compose) o uso del cloud SaaS

**El usuario es dueño literal de su data.** Cloud cifrado o self-host: ambas opciones desde día 1.

### El problema real (no lo que se ve a primera vista)

> "Cada médico se basa sobre su último resultado y un resumen mal contado del médico anterior. Imposible contar lo relevante en 5 minutos de cita."
> — *Santiago Patiño, 2026-05-04*

El RAG es la plomería. **El producto real es eliminar el contexto pobre/sesgado que recibe cada médico al inicio de cada consulta.** El usuario no puede ser un buen agente RAG de su propia historia clínica en 5 minutos. AdelIA lo hace por él.

---

## 2. No-goals (qué NO es AdelIA en v0.1)

- **No es un dispositivo médico** (no MDR/CE, no FDA). Es un *personal documentation tool*.
- **No es un sistema de toma de decisiones clínicas.** AI puede equivocarse, médico siempre verifica.
- **No reemplaza al EHR del hospital.** Es la copia personal del paciente.
- **No es un marketplace de médicos** ni hace teleconsulta.
- **No graba citas en vivo en v0.1** (eso es v0.2). v0.1 acepta audios ya grabados subidos manualmente.
- **No integra con portales nacionales de salud en v0.1** (Mon Espace Santé, Sanidad ES) — eso es v0.3.
- **No tiene WhatsApp en v0.1** — Telegram sí, WA en v0.2.

## 3. Target users

### Primary persona — "Padre/cuidador con hijo con condición crónica o multi-especialista"

- Maneja historia clínica fragmentada (varios médicos, países, idiomas)
- Reentra en cada cita con contexto roto
- Tiene ya muchos PDFs, fotos, recetas dispersas
- Es técnicamente competente para usar una app web/móvil

### Secondary personas

- Adulto con condición crónica (diabetes, autoinmune, oncología)
- Persona viviendo entre países (expat, dual-residencia)
- Médico que recibe el briefing (consumidor secundario, no usuario directo en v0.1)

### NO son target en v0.1

- Personas sin historia clínica acumulada (caso "sano sin antecedentes")
- Usuarios que requieren UX 100% no-técnica (grandma killer — backlogged a v0.2+)
- Usuarios que necesitan compliance HIPAA/MDR formal (v0.4+ si validamos product-market fit)

## 4. Casos de uso v0.1 (user journeys)

### UJ-1: Onboarding + ingesta inicial bulk
1. Usuario crea cuenta (email + password, o magic link)
2. Configura BYOK (opcional) — pega API key de OpenAI/Anthropic/Mistral. Si no, usa free fallback (Mistral La Plateforme / Groq).
3. Setup forwarding email: app le da `<id>@in.adelia.app` (placeholder). Usuario crea filtro Gmail "from:cualquier-clínica → forward".
4. Usuario forwardea histórico de emails con PDFs (10-50 PDFs típico) → ingesta automática.
5. Usuario vincula Telegram bot (`/start` con código → cuenta vinculada). Reenvía PDFs/fotos/audios → ingesta.
6. Sistema procesa: OCR → extracción entidades médicas → embeddings → timeline.
7. Usuario ve timeline + summary auto-generado.

### UJ-2: Pre-consulta briefing
1. Usuario tiene cita médica el martes (pediatría, cardiología, etc).
2. Domingo abre AdelIA → "Crear briefing para próxima cita".
3. Selecciona especialidad + motivo de consulta (libre texto opcional).
4. Sistema genera 1-pager con:
   - 🚨 Red flags relevantes
   - 💊 Medicación activa
   - 🧪 Labs recientes (últimos 3 meses)
   - 🏥 Diagnósticos previos relacionados con la especialidad
   - 🧬 Antecedentes familiares relevantes
   - 📅 Timeline visual
   - ❓ Q&A pre-baked: top 5 preguntas que el especialista probablemente hará, ya respondidas con citas a fuente (PDF pág X)
   - 💬 Espacio para chat libre del médico
5. Usuario revisa, ajusta TTL (1h/24h/7d), pulsa "Compartir" → genera signed URL + QR + PDF.

### UJ-3: En la consulta (sharing flow)
1. Usuario abre AdelIA en su móvil. Ve QR del briefing actual.
2. Médico escanea QR → abre briefing en SU móvil/laptop. Lee en 30 segundos.
3. (Opcional) Médico hace una pregunta en el chat libre: *"¿Cuándo fue la última vacuna del meningococo?"* → RAG responde con cita.
4. Después de la consulta, usuario revoca link (1 click) o deja expirar.

### UJ-4: Consulta ad-hoc
1. Usuario abre app, va a "Chat".
2. Pregunta: *"¿Qué antibiótico le dieron en febrero 2024 y a qué dosis?"*
3. RAG responde con cita a fuente exacta (PDF, pág, fecha).
4. (Variante) Usuario pregunta: *"Dame la curva de azúcar de los últimos 10 años"* → sistema genera gráfica temporal a partir de entidades extraídas.

## 5. Arquitectura (high-level)

```
┌─ INGESTION (multimodal) ────────────────────────────────┐
│  Web DnD │ Email Forward │ PWA Cámara │ Telegram Bot   │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─ INGESTION PIPELINE (Celery workers) ───────────────────┐
│  1. File ingest (S3/MinIO) + mime detect                │
│  2. OCR (Mistral OCR API / Tesseract self-host)         │
│  3. Audio transcribe (Whisper API / whisper.cpp)        │
│  4. Medical entity extractor (LLM, structured output)   │
│  5. Chunker + embedder (pgvector)                       │
│  6. Timeline event builder                              │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─ STORAGE ───────────────────────────────────────────────┐
│  Postgres + pgvector:                                    │
│   - documents(raw text, metadata)                        │
│   - chunks(content, embedding, doc_ref)                  │
│   - entities(type, value, date, doc_ref, confidence)     │
│   - timeline_events(date, type, summary, source_refs)    │
│   - user_settings (BYOK, sharing defaults)               │
│  S3 / MinIO: blobs originales (PDFs/audios/imgs)         │
│  Redis: queue Celery + cache LLM responses               │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─ QUERY / BRIEFING LAYER ────────────────────────────────┐
│  Free Chat (RAG) │ Briefing Generator                    │
│                  │  ├─ Specialty templates (rule-based) │
│                  │  ├─ Q&A pre-baker (LLM predict + RAG)│
│                  │  └─ Citation enforcer                │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─ SHARING / DELIVERY ────────────────────────────────────┐
│  Signed URL (HMAC) + TTL configurable + revocable       │
│  Surfaces: QR │ Copy-link │ PDF (WeasyPrint) │ Email Dr │
└─────────────────────────────────────────────────────────┘
```

### Boundaries / unidades clave

Cada unidad tiene un propósito único, interface clara, y se puede entender/testear por separado:

1. **`ingest_service`** — recibe archivos de cualquier surface (web/email/PWA/Telegram), guarda en S3, encola job Celery. *Test*: file in → S3 + queued job. No conoce LLMs ni RAG.
2. **`extraction_workers`** — Celery workers que ejecutan: OCR / transcribe / entity extract / embed. *Test*: file ref in → entities + chunks out. No conoce sharing.
3. **`rag_service`** — interfaz unificada al RAG (chat + briefing). Hace retrieval + generation + citation. *Test*: query + filter → answer + citations. No conoce ingesta.
4. **`briefing_service`** — orquesta el briefing (template selection por especialidad + Q&A pre-bake + render). Llama a `rag_service`. *Test*: specialty + user_id → briefing.json.
5. **`sharing_service`** — genera signed URLs, QR, PDF; valida acceso; revoca. *Test*: briefing_id + TTL → URL + QR + PDF; revocation works.
6. **`auth_service`** — Auth.js wrapper con BYOK encryption (envelope encryption con KMS o user-derived key).
7. **`web_app`** (Next.js + PWA) — UI + cliente HTTP. No tiene lógica de negocio.

Estas 7 unidades se pueden contribuir/refactorear independientemente. Es la base para que sea un OSS sostenible.

## 6. Data model (Postgres)

```sql
-- Tabla de documentos crudos
CREATE TABLE documents (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL,
  source TEXT NOT NULL CHECK (source IN ('web','email','pwa_camera','telegram','manual')),
  mime_type TEXT NOT NULL,
  s3_key TEXT NOT NULL,
  raw_text TEXT,                -- post-OCR/transcribe
  metadata JSONB,               -- sender_email, telegram_msg_id, original_filename...
  created_at TIMESTAMPTZ DEFAULT now(),
  processed_at TIMESTAMPTZ
);

-- Embeddings para RAG
CREATE TABLE chunks (
  id UUID PRIMARY KEY,
  document_id UUID REFERENCES documents(id) ON DELETE CASCADE,
  user_id UUID NOT NULL,
  content TEXT NOT NULL,
  embedding vector(1024),       -- pgvector; 1024 dim para Mistral embed / 1536 OpenAI
  chunk_index INT NOT NULL,
  metadata JSONB                -- page, section, etc
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

-- Entidades médicas extraídas
CREATE TABLE entities (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL,
  document_id UUID REFERENCES documents(id) ON DELETE CASCADE,
  entity_type TEXT NOT NULL,    -- medication|lab_result|diagnosis|allergy|vaccine|family_hx|vital
  name TEXT NOT NULL,           -- "Amoxicillin" / "Glucose" / "Type 2 Diabetes"
  value JSONB,                  -- {"dose":"500mg","route":"oral"} | {"value":98,"unit":"mg/dL"}
  event_date DATE,
  confidence FLOAT,             -- 0.0-1.0 LLM self-rated
  raw_quote TEXT,               -- texto original (para citation)
  page INT,
  created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ON entities (user_id, entity_type, event_date);

-- Timeline events (vista derivada para queries temporales rápidas)
CREATE MATERIALIZED VIEW timeline_events AS
SELECT id, user_id, entity_type as type, name, value, event_date, document_id
FROM entities
WHERE event_date IS NOT NULL
ORDER BY user_id, event_date DESC;

-- Briefings generados
CREATE TABLE briefings (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL,
  specialty TEXT NOT NULL,       -- 'pediatrics'|'cardiology'|'endocrinology'|...
  reason TEXT,                   -- texto libre del usuario
  payload JSONB NOT NULL,        -- briefing renderizado completo (sections + Q&A)
  generated_at TIMESTAMPTZ DEFAULT now()
);

-- Sharing
CREATE TABLE share_links (
  id UUID PRIMARY KEY,
  briefing_id UUID REFERENCES briefings(id) ON DELETE CASCADE,
  user_id UUID NOT NULL,
  token TEXT UNIQUE NOT NULL,    -- HMAC-signed
  expires_at TIMESTAMPTZ NOT NULL,
  revoked BOOLEAN DEFAULT false,
  access_count INT DEFAULT 0,
  last_accessed_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- BYOK + settings
CREATE TABLE user_settings (
  user_id UUID PRIMARY KEY,
  llm_provider TEXT,             -- 'openai'|'anthropic'|'mistral'|'free'
  api_key_encrypted BYTEA,       -- envelope-encrypted con master key
  default_share_ttl_seconds INT DEFAULT 86400,
  email_forwarding_id TEXT UNIQUE,  -- e.g. "x7k9m2" → x7k9m2@in.adelia.app
  telegram_chat_id BIGINT
);
```

### Notas de diseño data model

- **`entities` es la goldmine**: extracción estructurada permite queries temporales (curva azúcar) y briefings reproducibles. Es la diferencia entre RAG genérico y RAG médico útil.
- **`raw_quote` en cada entity** es crítico: permite citación verificable. Sin esto, el médico no confía en el briefing.
- **`confidence` self-rated por LLM** + flag manual de revisión. Bajo confidence → marcar para revisión humana (UX feature en v0.2).
- **Soft-delete + GDPR right-to-erase**: `documents.deleted_at` + cascade. Real delete via job nocturno.

## 9. Compliance posture

### Postura: Personal Documentation Tool, no Medical Device

AdelIA NO es un dispositivo médico bajo EU MDR ni FDA. Es una herramienta de documentación personal. Esto es **deliberado y crítico** para la viabilidad del proyecto OSS — la certificación MDR Class IIa cuesta años y €€€.

### Disclaimers (visibles en UI + briefing)

- **App home + first-run**: *"AdelIA is a personal documentation tool, not a medical device. It does not provide medical advice. Always verify with your healthcare professional."*
- **Briefing footer (visible al médico)**: *"Patient-curated data, not authenticated by healthcare provider. AI-generated summaries may contain errors. This document does not replace clinical judgment."*
- **Chat responses**: *"This information is from your records. AI may make mistakes — always verify with a qualified provider."*

### GDPR

- Data del usuario = el usuario es controller, AdelIA es processor (cloud SaaS) o el usuario procesa su propia data (self-host).
- DPA template para usuarios cloud SaaS.
- Data portability: export completo en JSON + ZIP de blobs originales (1 click).
- Right to erasure: hard delete completo en <30 días, audit log.
- DPO: TBD (Santiago como DPO inicial; cuando >100 usuarios, contratar uno).
- Hosting: regiones EU only por default (Frankfurt/París) en SaaS cloud.

### Encryption

- **At-rest**: Postgres encryption volume + S3 server-side encryption.
- **In-transit**: TLS 1.3.
- **BYOK API keys**: envelope encryption — clave master AdelIA cifra una clave por-usuario; clave por-usuario cifra los API keys. Master key en KMS/Vault.
- **Sharing tokens**: HMAC con clave rotable mensualmente.
- **Self-host**: usuario maneja todas las keys; documentación clara.

### NO tocamos en v0.1

- HIPAA: ni intentamos. US users con disclaimer "not HIPAA-compliant; not for use as PHI in covered entities".
- ISO 27001 / SOC2: prematuro. Posible v0.4+ si SaaS escala.
- CE MDR / FDA: no aplicable mientras seamos *documentation tool*.

## 10. License: AGPL-3.0

**AGPL-3.0 elegida deliberadamente.**

Razones:
1. **Coherente con "tú dueño de tu data"**: copyleft fuerte previene fork propietario.
2. **Previene SaaS rip-off**: AWS/GCP no pueden levantar "AdelIA hosted" propietario sin contribuir cambios. Modelo MongoDB/Elastic-pre-relicensing pre-incidente.
3. **Hosted SaaS de AdelIA cumple AGPL** porque liberamos todo el código.
4. **Self-hosters individuales**: no obligación adicional (uso personal).
5. **Empresas que self-hosteen**: deben publicar cualquier modificación (alineado con espíritu del proyecto).

Alternativas descartadas:
- **MIT/Apache**: permite fork propietario, mata sostenibilidad si AWS lo levanta.
- **BSL (Business Source License)**: source-available pero NO OSI-OSS, mata adopción developer.
- **Elastic License v2**: similar problema BSL.

CLA: **No CLA** inicialmente. DCO (sign-off) suficiente. Si necesitamos relicensing en futuro, evaluamos.

## 11. Roadmap

### v0.1 — Pre-consulta briefing (este spec)
**Objetivo**: usuario carga histórico, genera briefing pre-consulta, comparte con médico.
**Timeline target**: 4-6 semanas solo, si full-time. ~10-12 semanas part-time.
**Done = demo end-to-end**: forward 10 PDFs, generar briefing pediatría, compartir QR, verificar render.

### v0.2 — Live recording + WhatsApp + hosted subscription (~3 meses post-v0.1)
- Recording consulta en vivo (PWA mobile + Whisper + extracción auto)
- WhatsApp Business API ingestion
- Hosted subscription tier ($5/mes, queries ilimitadas con LLM cloud Mistral medium)
- Marcado low-confidence entities + UX revisión humana

### v0.3 — Doctor query mode + portales nacionales (~6 meses post-v0.1)
- Doctor query directo (médico hace preguntas en su dispositivo, paciente da consentimiento por sesión)
- Integración Mon Espace Santé (FR, FHIR API)
- Integración Sanidad ES (CCAA específicas, comenzar por Madrid/Cataluña)
- Multi-perfil (un usuario gestiona perfiles de hijos/padres mayores)

### v0.4+ — Backlog
- Mobile native (iOS/Android) si PWA no escala
- HIPAA compliance path (US market)
- Marketplace de templates por especialidad (community-contributed)
- Federación: usuarios pueden compartir briefings entre instancias self-hosted
- Compliance MDR Class I/IIa (si producto valida market fit serio)

## 13. Riesgos conocidos

| Riesgo | Severidad | Mitigación |
|--------|-----------|------------|
| Calidad OCR mala en PDFs médicos antiguos/escaneados | Alta | Mistral OCR + retry con Tesseract; flag low-confidence; UX revisión manual |
| LLM extracción inventa entidades médicas | **Crítica** | Structured output + JSON schema validation + confidence scoring + raw_quote citation obligatoria. Reject si quote no aparece textualmente en raw_text. |
| Médicos no escanean QR en consulta (no usan móvil) | Media | PDF print fallback en mismo flujo |
| Coste LLM si usuarios no tienen BYOK y abusan free tier | Media | Rate limit por usuario en free fallback (10 queries/día Mistral free tier es limit upstream) |
| Compliance creep: alguien usa para decisión clínica → demanda | Alta | Disclaimers omnipresentes + ToS clara + log de disclaimers aceptados |
| Self-host es complejo, nadie lo usa, "tú dueño" es vacío | Alta | Docker compose 1-comando + docs paso-a-paso + tutorial vídeo en v0.1.1 |
| Adopción cero porque ingestion sigue siendo fricción | Crítica | Email forwarding + Telegram bot apuntan a fricción mínima; medir tasa de carga histórico en primera semana |
| Audio recording (v0.2) tiene problemas legales en algunos países | Media | Investigar país-por-país; default opt-in con doctor consent prompt |

## 14. Métricas de éxito v0.1

- **Activación**: 70% de usuarios registrados sube ≥3 documentos en primera semana.
- **Aha moment**: 50% de usuarios genera ≥1 briefing en primer mes.
- **Sharing real**: 30% de briefings se comparten (link/QR/PDF/email) al menos 1 vez.
- **Retención técnica**: <5% pérdida de data por bugs en ingesta.
- **Performance**: briefing generation P95 <30 segundos.
- **Self-host viability**: ≥10 instancias self-hosted en GitHub stars/Issues sin pedirnos soporte.

Si no hay 50 usuarios activos a los 3 meses post-launch, evaluar pivot.
