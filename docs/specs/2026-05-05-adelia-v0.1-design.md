# AdelIA — v0.1 Design Spec

## 1. Visión

**AdelIA es una plataforma open source de soberanía de datos médicos personales con análisis IA en 2 modos.**

Cada usuario:
1. Vuelca TODA su historia clínica (PDFs, fotos, labs, audios, recetas) en su vault personal — un FHIR-IPS bundle propio, exportable, portable.
2. Analiza esa data con IA en **2 modos**:
   - **Modo A — Self-analysis**: pregunta a tu data en lenguaje natural ("dame la curva de azúcar de los últimos 10 años", "¿qué antibióticos he tomado?", "tendencia de mi colesterol").
   - **Modo B — Briefing para médico**: genera un 1-pager opinionado, formato SBAR, max 1 página, filtrado por especialidad, para compartir con cualquier especialista (no solo pediatra) vía link efímero, PDF o email.
3. Auto-hosting completo (Docker Compose) o cloud SaaS hosted en `adelia.godi.ai`.

**Tú eres dueño literal de tu data.** Modo A te da independencia analítica; Modo B te da contexto compartible para cualquier consulta médica.

### El pain real (driver del diseño)

> "Cada médico se basa sobre su último resultado y un resumen mal contado del médico anterior. Imposible contar lo relevante en 5 minutos de cita."
> — *Santiago Patiño, 2026-05-04*

> "Tenemos control y un lugar único mío para guardar mis datos médicos y analizarlos con IA con ayuda de un médico o yo mismo."
> — *Santiago Patiño, 2026-05-06 (reframe del core)*

El RAG es la plomería. **El producto real son las dos cosas que la sanidad fragmentada no te da hoy**: análisis longitudinal personal de TUS datos + briefing portable que cualquier médico entiende en 30 segundos.

## 2. No-goals (qué NO es AdelIA en v0.1)

- **No es un dispositivo médico** (no MDR/CE, no FDA). Es *personal documentation tool*.
- **No es sistema de toma de decisiones clínicas.** AI puede equivocarse, médico siempre verifica.
- **No reemplaza al EHR del hospital.** Es la copia personal del paciente.
- **No es marketplace de médicos** ni hace teleconsulta.
- **No graba citas en vivo en v0.1** (eso es v0.2). v0.1 acepta audios subidos manualmente.
- **No integra con portales nacionales en v0.1** (Mon Espace Santé, Sanidad ES) — v0.3.

### Cortes específicos de v0.1 (deferred a v0.1.1) por capacidad de tiempo (1h/día)

- ❌ **Telegram bot** → v0.1.1
- ❌ **Email forwarding** ingestion → v0.1.1
- ❌ **PWA installable + cámara** → v0.1.1 (web upload con file picker acepta fotos en v0.1)
- ❌ **i18n EN + FR UI** → v0.1.1 (arquitectura `next-intl` desde día 1, pero solo strings ES en v0.1)
- ❌ **Celery + Redis queue** → v0.1.1 (FastAPI BackgroundTasks suficiente para volumen v0.1)
- ✂️ **Specialty templates**: 1 universal SBAR + filtros por especialidad (no 8 templates distintos)
- ✂️ **Sharing surfaces**: signed link + PDF (sin QR widget separado, sin email-to-doctor — surfaces extra en v0.1.1)

## 3. Target users

### Primary persona — "Adulto técnicamente competente con historia clínica fragmentada"

Generaliza más allá del caso pediátrico. Incluye:
- Padre/cuidador gestionando historia médica de hijo
- Adulto con condición crónica (diabetes, autoinmune, oncología)
- Persona viviendo entre países (expat, dual-residencia)
- Cualquier persona con >5 médicos distintos en últimos 3 años

Pain común: data fragmentada, contexto roto en cada consulta, decisiones IA que no puedes hacer en una app de 1 médico.

### NO son target en v0.1

- Personas sin historia clínica acumulada
- Usuarios que requieren UX 100% no-técnica (deferred a v0.2+ con onboarding asistido)
- Usuarios que necesitan compliance HIPAA/MDR formal (v0.4+ post product-market fit)

## 4. Casos de uso v0.1 (user journeys)

### UJ-1: Onboarding + ingesta inicial bulk
1. Usuario crea cuenta (magic link via email).
2. Configura BYOK (opcional) — pega API key OpenAI/Anthropic/Mistral. Si no, free fallback (Mistral La Plateforme / Groq).
3. Web upload: drag-drop bulk de PDFs/imágenes/audios (típicamente 10-50 archivos en primer batch).
4. Sistema procesa (FastAPI BackgroundTasks): mime detect → OCR (Mistral OCR) → audio transcribe (Whisper) → entity extraction (LLM structured output con `provenance="extracted_from_clinician_doc"`) → embeddings → timeline event builder.
5. Usuario ve timeline + summary auto-generado. Indicators de processing en tiempo real (SSE o polling).

### UJ-2: Modo A — Self-analysis chat (primary)
1. Usuario abre AdelIA, va a "Chat".
2. Pregunta: *"¿Qué antibiótico le dieron en febrero 2024 y a qué dosis?"*
3. RAG retrieval (pgvector) sobre todo el FHIR-IPS bundle del usuario → LLM responde con cita a fuente exacta (PDF, página, fecha).
4. Variantes:
   - *"Dame la curva de azúcar de los últimos 10 años"* → query temporal sobre `entities` (entity_type=`observation`, name=`glucose`) → renderiza gráfica time-series.
   - *"Tendencia de mi colesterol y cuándo se disparó"* → análisis trend.
   - *"¿He tomado algún antiinflamatorio en los últimos 6 meses?"* → filter sobre `medication`.
5. Cada respuesta incluye **citación obligatoria** al `raw_quote` de la fuente. Sin quote verificable → respuesta marcada *"unverified"*.

### UJ-3: Modo B — Briefing para médico
1. Usuario tiene cita el martes con un especialista (cualquier especialidad).
2. Domingo abre AdelIA → "Crear briefing para próxima cita".
3. Selecciona especialidad target (dropdown con ~12 especialidades) + motivo de consulta (texto libre, opcional pero recomendado).
4. Sistema genera 1-pager SBAR-shaped (ver §7 Briefing Schema) con:
   - **S - Situation**: motivo de consulta + edad/género + 1 línea de contexto
   - **B - Background**: 8 secciones universales rankeadas, filtradas por especialidad
   - **A - Assessment**: trends y red flags relevantes (LLM-generated, marked AI-generated)
   - **R - Open questions**: top 5 preguntas que el especialista probablemente hará, ya respondidas con citas
5. Usuario revisa, ajusta TTL (1h/24h/7d), pulsa "Compartir" → genera signed URL + PDF descargable.

### UJ-4: Sharing flow
1. Usuario abre AdelIA en su móvil. Ve link compartible del briefing actual + botón "Descargar PDF".
2. Surface v0.1: signed link + PDF.
3. Variantes de uso:
   - Mandar link por WhatsApp/email al médico **antes** de la consulta (asíncrono).
   - Imprimir PDF y llevarlo a la consulta (low-tech fallback).
4. Después de la consulta, usuario revoca link (1 click) o deja expirar.

> **v0.1.1 surfaces**: QR widget renderizable + email-to-doctor con consentimiento. La signed URL ya soporta múltiples superficies — solo es UX adicional.

### Boundaries / unidades clave (5 unidades v0.1)

Cada unidad: propósito único, interface clara, testeable independiente.

1. **`api_service`** (FastAPI) — endpoint web upload, auth (Auth.js bridge), orquesta BackgroundTasks. *Test*: file in → S3 + queued task. No conoce LLMs ni RAG.
2. **`extraction_pipeline`** — funciones puras llamadas desde BackgroundTasks: OCR / transcribe / entity extract / embed. *Test*: file ref in → entities + chunks out.
3. **`rag_service`** — interfaz unificada al RAG (Modo A chat + Modo B briefing). Hace retrieval + generation + citation enforcement. *Test*: query + filter → answer + citations.
4. **`briefing_service`** — orquesta briefing (SBAR envelope + 8 secciones + specialty filter rules + Q&A pre-bake). Llama a `rag_service`. *Test*: specialty + user_id → briefing.json.
5. **`sharing_service`** — genera signed URLs + PDF (WeasyPrint); valida acceso; revoca. *Test*: briefing_id + TTL → URL + PDF; revocation works.

`web_app` (Next.js + i18n architected con `next-intl`) consume los 5 anteriores.

## 6. Data model (Postgres)

### Principio: Two views, one dataset

- **Storage layer** = bundle FHIR-IPS completo del usuario, todas las entidades, sin opinión, soporta Modo A.
- **Briefing** = proyección OPINIONADA generada en share-time (no almacenada como dato canónico, solo como `briefing` cacheado).

### Schema

```sql
-- Documentos crudos
CREATE TABLE documents (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL,
  source TEXT NOT NULL CHECK (source IN ('web','manual')),
  -- v0.1.1: agregar 'email','pwa_camera','telegram'
  mime_type TEXT NOT NULL,
  s3_key TEXT NOT NULL,
  raw_text TEXT,                -- post-OCR/transcribe
  metadata JSONB,
  created_at TIMESTAMPTZ DEFAULT now(),
  processed_at TIMESTAMPTZ,
  deleted_at TIMESTAMPTZ        -- soft delete + GDPR cascade
);

-- Embeddings para RAG
CREATE TABLE chunks (
  id UUID PRIMARY KEY,
  document_id UUID REFERENCES documents(id) ON DELETE CASCADE,
  user_id UUID NOT NULL,
  content TEXT NOT NULL,
  embedding vector(1024),       -- mistral-embed (1024 dim)
  chunk_index INT NOT NULL,
  metadata JSONB                -- page, section
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

-- Entidades médicas (FHIR-IPS aligned)
CREATE TABLE entities (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL,
  document_id UUID REFERENCES documents(id) ON DELETE CASCADE,
  -- FHIR R4 resource type
  entity_type TEXT NOT NULL CHECK (entity_type IN (
    'condition',          -- FHIR Condition (active problem / past illness)
    'medication',         -- FHIR MedicationStatement / MedicationRequest
    'allergy',            -- FHIR AllergyIntolerance
    'immunization',       -- FHIR Immunization
    'procedure',          -- FHIR Procedure (incl. surgical, implants)
    'observation',        -- FHIR Observation (labs, vitals, imaging conclusions)
    'family_history',     -- FHIR FamilyMemberHistory
    'device',             -- FHIR Device (implants, prosthetics)
    'allergen_reaction',  -- nested in AllergyIntolerance
    'social_history'      -- FHIR Observation cat=social-history
  )),
  -- código clínico estándar si disponible
  coding_system TEXT,    -- 'ICD10' | 'SNOMED' | 'LOINC' | 'ATC' | 'RxNorm' | null
  code TEXT,
  name TEXT NOT NULL,
  value JSONB,           -- estructura libre por tipo: {dose,route,freq} | {value,unit} | etc
  event_date DATE,
  status TEXT,           -- 'active' | 'resolved' | 'inactive' | 'completed'
  -- procedencia (clave para confianza clínica)
  provenance TEXT NOT NULL CHECK (provenance IN (
    'patient_stated',              -- usuario lo escribió manualmente
    'extracted_from_clinician_doc', -- LLM extrajo de doc clínico (PDF, lab, receta)
    'clinician_verified'            -- v0.2+: médico revisó y confirmó
  )),
  confidence FLOAT,      -- 0.0-1.0 LLM self-rated (NULL si patient_stated)
  raw_quote TEXT,        -- texto original verbatim — OBLIGATORIO si extracted_from_clinician_doc
  page INT,
  needs_review BOOLEAN DEFAULT false, -- flag UX: confidence < 0.7
  created_at TIMESTAMPTZ DEFAULT now(),
  deleted_at TIMESTAMPTZ
);
CREATE INDEX ON entities (user_id, entity_type, status, event_date DESC);

-- Vista derivada: timeline (queries temporales rápidas)
CREATE MATERIALIZED VIEW timeline_events AS
SELECT id, user_id, entity_type, name, value, event_date, document_id, provenance
FROM entities
WHERE deleted_at IS NULL AND event_date IS NOT NULL
ORDER BY user_id, event_date DESC;
CREATE INDEX ON timeline_events (user_id, event_date DESC);

-- Briefings generados (cache de proyecciones, no canonical data)
CREATE TABLE briefings (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL,
  target_specialty TEXT NOT NULL,
  reason_for_consult TEXT,     -- texto libre del usuario
  payload JSONB NOT NULL,      -- briefing rendered: SBAR + 8 sections + Q&A
  generated_at TIMESTAMPTZ DEFAULT now()
);

-- Sharing
CREATE TABLE share_links (
  id UUID PRIMARY KEY,
  briefing_id UUID REFERENCES briefings(id) ON DELETE CASCADE,
  user_id UUID NOT NULL,
  token TEXT UNIQUE NOT NULL,    -- HMAC-signed, opaque
  expires_at TIMESTAMPTZ NOT NULL,
  revoked BOOLEAN DEFAULT false,
  access_count INT DEFAULT 0,
  last_accessed_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Usuario settings + BYOK encriptado
CREATE TABLE user_settings (
  user_id UUID PRIMARY KEY,
  llm_provider TEXT,             -- 'openai'|'anthropic'|'mistral'|'free'
  api_key_encrypted BYTEA,       -- envelope encryption
  default_share_ttl_seconds INT DEFAULT 86400,
  preferred_locale TEXT DEFAULT 'es' -- 'es' v0.1; 'en','fr' v0.1.1
);
```

### Reglas de diseño data model (críticas)

1. **`raw_quote` obligatorio** si `provenance='extracted_from_clinician_doc'`. Si el LLM no puede citar verbatim del raw_text → reject la entity. Esto previene hallucination de entidades médicas.

2. **`confidence < 0.7` → `needs_review=true`** y se muestra en UI con badge "verificar" antes de incluir en briefing.

3. **"No known X" explícito** (regla IPS): si una entity_type requerida no tiene entries del usuario, el briefing debe explicitar *"No known allergies"* (no omitir la sección). El briefing service genera esto automáticamente para `allergy`, `medication`, `condition` (las 3 secciones obligatorias del kernel convergente).

4. **Soft-delete + GDPR right-to-erase**: `deleted_at` cascade. Hard delete via job nocturno >30d. Audit log inmutable.

5. **FHIR export**: endpoint `GET /api/users/me/fhir-bundle` retorna IPS-compliant FHIR R4 Bundle JSON. Data portability built-in (GDPR Art. 20).

## 7. Briefing schema (NEW — basado en research médica)

> Referencias: HL7 IPS v2.0.0 (ISO 27269:2021), FHIR R4 Clinical Summary Module, SBAR (AHRQ), GP referral letter convention (RACGP), AAFP problem-list literature, Apple Health Records, NHS Summary Care Record, Mon Espace Santé, Epic MyChart.

### 7.1 Envoltura SBAR (Situation–Background–Assessment–Recommendation)

Forma del briefing, optimizada para 30s lectura especialista:

```
┌─────────────────────────────────────────────────────────────┐
│  ADELIA BRIEFING · {patient_name} · {age/sex}              │
│  Generated: {timestamp}  ·  Target specialty: {specialty}   │
│  ⚠ Patient-curated data, not authenticated by HCP.          │
├─────────────────────────────────────────────────────────────┤
│  SITUATION                                                   │
│   ▸ Reason for this consult: {reason_for_consult}           │
│   ▸ 1-line context: {age, sex, key relevant background}     │
├─────────────────────────────────────────────────────────────┤
│  BACKGROUND (8 secciones universales filtradas)             │
│   1. Active Problems                                         │
│   2. Current Medications                                     │
│   3. Allergies & Adverse Reactions                          │
│   4. Recent Relevant Results (3-6 mo)                       │
│   5. Past Procedures & Implants                             │
│   6. Vitals & Biometrics (latest)                           │
│   7. [conditional] Immunizations (only if peds/ID/travel)   │
│   8. [conditional] Family History (only if onco/genetics)   │
├─────────────────────────────────────────────────────────────┤
│  ASSESSMENT (AI-generated, marked)                          │
│   ▸ Recent trends and red flags relevant to specialty       │
│   ▸ Notes on data gaps / low-confidence entries             │
├─────────────────────────────────────────────────────────────┤
│  OPEN QUESTIONS (Q&A pre-baked)                             │
│   ▸ Top 5 preguntas anticipadas del especialista, con citas │
│   ▸ "Free chat" link para queries ad-hoc del médico         │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 Las 8 secciones universales — ranking y reglas

| # | Sección | FHIR resource | IPS | Always shown? | Notas |
|---|---------|---------------|-----|---------------|-------|
| 1 | **Reason for consult** | (header) | – | ✓ siempre | #1 valor para especialista. SBAR Situation. |
| 2 | **Active Problems** | Condition (status=active) | R | ✓ siempre | Distingue active vs resolved (regla AAFP). |
| 3 | **Current Medications** | MedicationStatement | R | ✓ siempre | Si vacío: *"No known active medications"*. |
| 4 | **Allergies & Reactions** | AllergyIntolerance | R | ✓ siempre | Si vacío: *"No known allergies"*. Safety-critical. |
| 5 | **Recent Results** | Observation (last 3-6 mo) | S | ✓ siempre | Filter abnormal o trending. NO dump completo. |
| 6 | **Past Procedures + Implants** | Procedure + Device | S | ✓ siempre | Crítico para imaging/anestesia. |
| 7 | **Vitals & Biometrics** | Observation (vital-signs) | S | ✓ siempre | BP, HR, weight, BMI. Latest only. |
| 8 | **Family History** | FamilyMemberHistory | O | conditional | Si especialidad ∈ {oncology, genetics, cardio} OR patient flag. |

**Secciones explícitamente OMITIDAS por defecto** (keep en storage, hide en briefing salvo specialty match):
- **Immunizations** → hide salvo `specialty ∈ {pediatrics, infectious_disease, travel_medicine, oncology}` (research: AAFP + Apple/Epic priorities).
- **Past Medical History (resolved)** → hide salvo relevancia explícita (literature warns vs cluttering active problem list).
- **Social History** → hide salvo `specialty ∈ {hepatology, pulmonology, addiction_med}`.
- **Functional Status / Advance Directives** → hide salvo `specialty ∈ {geriatrics, palliative}`.
- **Plan of Care narrative** → siempre omit (pertenece al *próximo* clínico, no al briefing del paciente).
- **Long pasted lab tables** → siempre summarize, nunca paste.

### 7.3 Specialty filter rules (config-driven)

Implementado como JSON config en `packages/specialty-templates/`:

```json
{
  "pediatrics": {
    "include_immunizations": true,
    "highlight_growth_curves": true,
    "vital_emphasis": ["weight_percentile", "height_percentile"]
  },
  "endocrinology": {
    "highlight_labs": ["glucose", "HbA1c", "TSH", "T4"],
    "show_temporal_trends": true
  },
  "cardiology": {
    "highlight_labs": ["lipid_panel", "troponin"],
    "vital_emphasis": ["BP", "HR"],
    "include_family_history": true
  },
  "oncology": { "include_family_history": true, "include_immunizations": true },
  "default": { "include_immunizations": false, "include_family_history": false }
}
```

v0.1 ships con: `pediatrics`, `endocrinology`, `cardiology`, `gynecology`, `gastroenterology`, `dermatology`, `general_medicine`, `default`. Más en v0.1.1+.

### 7.4 Q&A pre-baker

LLM call con prompt: *"Given this patient's data, generate the top 5 questions a {specialty} specialist will most likely ask in a 15-minute consultation. For each question, provide the answer with citation to the source document."*

Resultado: array de `{question, answer, citations: [{doc_id, page, raw_quote}]}`. Renderizado en sección "Open Questions" del briefing.

### 7.5 Provenance enforcement

Cada item del briefing muestra badge:
- 🟢 `clinician_verified` (v0.2+, vacío en v0.1)
- 🟡 `extracted_from_clinician_doc` (con cita verificable a fuente)
- 🟠 `patient_stated` (explícito: "patient-reported, unverified")

Sin provenance → no aparece en briefing.

### Decisión Fly.io vs alternativas (resuelto)

- **Fly.io ✓** — Docker-native, parity con self-host, Postgres + persistent volumes integrado, multi-servicio escalable independiente, pricing predecible (~$5-15/mes inicial v0.1).
- ❌ Railway — UX simple pero costo escala rápido con 4+ servicios.
- ❌ Hetzner Cloud + Coolify — más barato (~€5/mes VPS) pero más mantenimiento manual; reservado para si traction requiere optimizar costo.

## 10. Compliance posture

### Postura: Personal Documentation Tool, not Medical Device

AdelIA NO es dispositivo médico bajo EU MDR ni FDA. Esto es **deliberado** — la certificación MDR Class IIa cuesta años y €€€, mata viabilidad OSS.

### Disclaimers (visibles en UI + briefing)

- **App home + first-run** (banner persistent): *"AdelIA is a personal documentation tool, not a medical device. It does not provide medical advice. Always verify with your healthcare professional."*
- **Briefing footer** (visible al médico): *"Patient-curated data, not authenticated by healthcare provider. AI-generated summaries may contain errors. This document does not replace clinical judgment."*
- **Chat responses (Modo A)**: footer *"AI may make mistakes — verify with a qualified provider before acting."*

### GDPR

- Data del usuario = el usuario es controller, AdelIA es processor (cloud SaaS) o el usuario procesa su propia data (self-host).
- DPA template para cloud SaaS users.
- **Data portability**: export FHIR R4 Bundle JSON + ZIP de blobs originales (1 click, GDPR Art. 20).
- **Right to erasure**: hard delete <30d, audit log immutable.
- DPO: Santiago inicial; contratar uno cuando >100 usuarios cloud.
- Hosting: **Fly.io regiones EU only** (Frankfurt `fra` / París `cdg`) por default en SaaS.

### Encryption

- **At-rest**: Postgres encryption volume + S3 server-side encryption.
- **In-transit**: TLS 1.3 enforced.
- **BYOK API keys**: envelope encryption — AdelIA master key cifra clave por-usuario; clave por-usuario cifra los API keys. Master key en Fly secrets / Vault.
- **Sharing tokens**: HMAC con clave rotable mensualmente.
- **Self-host**: usuario maneja todas las keys; documentación clara en `docs/deployment/secrets.md`.

### NO tocamos en v0.1 (intencional)

- HIPAA: ni intentamos. US users con disclaimer "not HIPAA-compliant".
- ISO 27001 / SOC2: prematuro. Posible v0.4+ si SaaS escala.
- CE MDR / FDA: no aplicable mientras seamos *documentation tool*.

## 14. Risks + mitigaciones

| Riesgo | Severidad | Mitigación |
|--------|-----------|------------|
| **Calidad OCR mala en PDFs antiguos/escaneados** | Alta | Mistral OCR + fallback Tesseract; flag low-confidence; UX revisión manual v0.1.1 |
| **LLM extracción inventa entidades médicas** | **Crítica** | Structured output + JSON schema validation + `raw_quote` obligatorio; reject si quote no aparece textualmente en raw_text |
| **Briefing pierde info crítica al filtrar por especialidad** | Alta | Default conservador (mostrar más); permite usuario override "show all sections" |
| **Coste LLM si usuarios no tienen BYOK abusan free tier** | Media | Rate limit 10 queries/día por usuario en free fallback (Mistral Plateforme limit upstream igual) |
| **Compliance creep: alguien usa para decisión clínica → demanda** | Alta | Disclaimers omnipresentes + ToS clara + log timestamps de disclaimer aceptado |
| **Self-host complejo, nadie lo usa, "tú dueño" es vacío** | Alta | `docker compose up` 1 comando + docs paso-a-paso + tutorial vídeo en v0.1.1 |
| **Adopción cero porque ingestion sigue siendo fricción incluso con web** | Crítica | v0.1 mide tasa upload primer-día; si <50% usuarios suben ≥3 docs en sem 1 → priorizar Telegram/email forwarding antes que continuar v0.1.1 roadmap |
| **🆕 Momentum risk: 1h/día durante 2-3 meses → project rot** | **Crítica** | (a) Spec + plan claros; (b) Claude Code leverage máximo en boilerplate/tests; (c) milestones quincenales públicos en GitHub; (d) "no skip days" rule (15 min mínimo) |
